# AI履歴から抽出した公開運用ガイドライン

## 目的

Claude CodeとCodexのローカル履歴から、繰り返し必要になった判断だけを抽象化し、この公開リポジトリのルール・スキル・検証へ反映する。会話本文、秘密情報、顧客名、非公開URL、アカウント情報、個人パスは保存しない。

## 調査範囲

- Claude Code: 7,995メッセージ、76プロジェクト。
- Codex: 1,935セッション、2,860ユーザーメッセージ、40プロジェクト。
- Codex Memory DB: 保存済みmemoryレコードは0件。

Claude Codeの集計ではcredential-like文字列の警告が1件あった。値やプロンプト本文は取得・記載せず、このリポジトリへの転記対象から除外した。履歴は `/tmp` で集計し、集計JSONもリポジトリへ追加しない。

## 繰り返し現れた課題

### 1. ソース、実行時資産、公開物の境界

Markdownだけを移しても、テーマ、ロゴ、背景、講演固有画像が同じ安定パスに存在しなければ資料は再現できない。submoduleの存在も実行時パスの解決を保証しない。

採用ルール:

- `brands/{brand}/` にテーマとブランド画像の固定実体を置く。
- `assets/shared/` と `assets/images/{year}/` をブランドから分離する。
- `vendor/` は更新元に限定し、スライド本文から直接参照しない。
- PDFは公開物、HTMLは検証生成物として扱う。

### 2. ルールの複製による不整合

README、AGENTS、CLAUDE、スキルに同じ手順を別表現で書くと、テーマパス、ビルド場所、公開物の扱いがずれる。

採用ルール:

- READMEは利用者の入口、AGENTSは実行規約、CLAUDEは構造と不変条件を担当する。
- 詳細なレビュー手順はスキルへ置き、AGENTSは正式な参照先だけを示す。
- Claude CodeとCodexで同じ成果条件を使い、ツール名だけを置き換える。

### 3. レビュー同士の局所最適

論理レビューは追加を求め、冗長性レビューは削除を求め、物語レビューやユーモアレビューは別の表現を加えやすい。個別には正しくても、同時適用すると時間超過や主張の変質が起きる。

採用スキル:

- `review-slide-suite` が中心の問い、約束、事実、時間、話者の声を基準に競合を解決する。
- 構造→スライド内の論理→理解容易性→主張と一次情報→論理校閲→敵対的検証→物語→認知リズム→冗長性→機知→文言の順を既定とする。
- 追加には時間コストまたは相殺する削除を必須とする。

### 4. 完了宣言と再現性のずれ

ローカルで一度ビルドできても、未追跡画像、初期化済みsubmodule、古いPDF、READMEのリンク切れが残ると公開リポジトリでは再現できない。

採用スキル:

- `prepare-slide-release` が公開前の検証順序を定義する。
- Marpの実ビルド、VCS差分、READMEリンク、clean cloneを直接確認する。
- clean cloneで2025年・2026年の代表資料を再ビルドする。

### 5. 深さを装う長文化

長い定型レポート、架空ペルソナ、根拠のない平均スコア、すべての指摘へのMarpコード追加は、レビューを深く見せても判断を改善しない。

採用ルール:

- 証拠→聴衆への影響→最小修正→コストの順で書く。
- 主張は機構、境界条件、反例、判断への含意で深める。
- 変更しない判断と保持すべき強みを明示する。
- 敵対的検証は指摘数のノルマを置かず、反証できない具体的な指摘だけを残す。
- 数値スコアは依頼された場合だけ使い、critical findingを平均で隠さない。

## 公開資産の構成

- 構成、スライド内の論理、論理校閲、理解容易性、主張、事実、反対意見、物語、認知リズム、冗長性、機知を扱う専門スキル。
- 初稿作成を行う `draft-slide-deck` と、文言を仕上げる `polish-slide-copy`。
- レビューを統合する `review-slide-suite`。
- 公開前検証を行う `prepare-slide-release`。
- AGENTS/CLAUDEのブランドパック、PDF、clean-clone規約。

## 採用しなかった候補

- 会話本文やmemoryの公開: 秘密情報と文脈依存情報を含むため不採用。
- 履歴由来の架空レビュアーペルソナ: 評価根拠を弱めるため不採用。
- すべてのPDFを自動更新する常時同期: 意図しない大容量差分を生むため不採用。変更対象を明示して検証する。
- submoduleをMarpの必須実行時パスにする構成: clone条件によって画像とCSSが欠落するため不採用。
- 自動同期・包括チェックスクリプト: 構造上の問題をスクリプトで覆い隠し、運用の理解を弱めるため不採用。
- 補助ツールが本当に必要な場合は、継続保守できるRust CLIとして設計する。
